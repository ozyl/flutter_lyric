# Apple Music 移动端渲染优化

## 2026-10-14：长歌词切行

反馈场景为小米 13 Pro、Android release/profile 模式下的长歌词切行。本轮没有连接真机，因此以下是代码路径与主机基准证据，不是手机帧率结论。

### 上轮遗漏的路径

上轮两个基准都在同一句内采样，没有跨过歌词时间边界。切行期间新旧两句同时浮动，仍然每字一个矩阵滤镜离屏层，文字越长合成开销越大。固定布局没有重排整首歌词，但 `_retarget` 还会为附近候选行无条件读取活动字号高度，提前创建本不需要的段落；LRC 模拟时间也会重复查询同一字素的裁剪框。

### 本轮实现

- 对纯色底色或完整纯色高亮的浮动字素，按视图 DPR 缓存中性字形图集，逐帧直接双线性采样。每字使用独立图集单元和透明边界，防止浮动时采到相邻字形；Word Pop、Float 的轨迹、时钟、字素与换行规则不变。
- 正在经过高亮边界的字、自定义渐变、未匹配时间的原色文本仍走现有绘制路径。保留尾部渐隐、透明颜色、RTL、距离模糊、行透明度和边缘遮罩。
- 图集使用 `Picture.toImageSync` 返回的图片句柄，不做逐帧 RGBA 回读。该 API 在 GPU 环境下可直接产生 GPU 图片，实际栅格化异步执行，详见 [Flutter API](https://api.flutter.dev/flutter/dart-ui/Picture/toImageSync.html)。不支持此 API 的旧引擎继续使用原路径，不提高 Flutter 2 / Dart 2.12 的库最低版本。
- 每视图最多保留 4 张图集，RGBA 像素预算合计 32 MiB、单张 8 MiB、边长最多 4096。这里不包含后端纹理/图层的额外开销。超限或图片生成失败时稳定回退，避免新旧长行相互驱逐、每帧重建。DPR、尺寸、字体、文字样式、文档变更和视图销毁会清理缓存。
- 将活动字号测量限制到需要字号过渡的旧式动画；复用与字素范围完全一致的词裁剪框，并预先缓存换行行段的左右边界。

图片采样与每帧重新栅格化文字在小数像素原点下可能有边缘抗锯齿差异。测试分别校验对齐原点下的像素、非对齐原点下的覆盖率/重心与内部颜色，以及独立字素运动，不能把两条路径宣称为任意变换下逐像素相同。

### 切行验证

新增 `test/benchmarks/apple_music_switch_benchmark.dart`：400 × 640 视口、DPR 3、24/48/72 字符、带翻译，分别使用真实词时间和 LRC 模拟时间。每组连续跨过 6 个新行，记录稳态及切行 0/16/64/128/240 ms 的 pump、额外 Picture 记录、显式 Canvas 图层/段落/图片绘制次数；可选测量 3x 栅格化与回读。

```sh
flutter test --no-pub --concurrency=1 \
  test/benchmarks/apple_music_switch_benchmark.dart \
  --dart-define=APPLE_MUSIC_RASTER=true --reporter expanded
```

新增 `test/lyric_transition_preparation_test.dart` 覆盖惰性段落和字素裁剪复用；`test/lyric_word_raster_test.dart` 覆盖图集预算、淘汰/释放、DPR/字体/样式/文档变化、长句命中、原路径回退、半透明高亮、换行及 RTL。原有像素合成参照仍保留。

2026-10-14，macOS arm64、Flutter 3.44.9 / Dart 3.12.2，以 `54379fc` 为优化前基线。同一份基准、同一 SDK 串行运行优化前后各 3 轮，以下取三轮 p50 的中位数。采样位置为切行 +64 ms；显式层数不包含边缘 ShaderMask 或后端内部 pass。

| 字符数 | 时间来源 | Canvas 离屏层：前 → 后 | Picture 记录：前 → 后 | raster + 回读：前 → 后 |
| --- | --- | ---: | ---: | ---: |
| 24 | 真实词时间 | 52 → 6 | 551 → 303 µs | 50.7 → 47.0 ms |
| 48 | 真实词时间 | 99 → 5 | 409 → 143 µs | 60.9 → 56.9 ms |
| 72 | 真实词时间 | 146 → 6 | 658 → 173 µs | 77.4 → 71.9 ms |
| 24 | LRC 模拟 | 52 → 6 | 153 → 131 µs | 49.2 → 47.2 ms |
| 48 | LRC 模拟 | 99 → 5 | 213 → 137 µs | 60.8 → 59.4 ms |
| 72 | LRC 模拟 | 146 → 4 | 309 → 166 µs | 74.4 → 71.1 ms |

缓存建立有一次性成本：真实词时间下首次进入新行的 +16 ms 帧，pump 的三轮 p50 中位数分别从 2.54/2.12/2.69 ms 增至 2.82/3.02/3.59 ms（24/48/72 字符）；模拟时间从 1.77/2.29/2.36 ms 增至 2.32/3.07/3.44 ms。该帧包含字形准备及图集 Picture 录制，后续帧复用缓存。因此，本轮证据是显著减少逐字合成与重复录制，不能宣称首次切行的所有工作都减少。整行模糊和边缘遮罩继续保留，主机总 raster + 回读改善仅约 2–7%。

主机 readback 测试会放大整行模糊及回读成本，不能将它换算为移动端 FPS。下一次真机验证仍应在小米 13 Pro 上记录切行前后 UI/raster 时间，覆盖冷启动、连续切行、暂停浮动、长句和快速 seek；如果还掉帧，需根据 trace 区分剩余整行模糊成本与首次图集栅格化成本。

## 第一轮优化记录（2026-10-13）

### 定位

Apple Music 默认开启 Character Float。即使播放暂停，只要当前歌词可见，Float 仍会按显示帧更新；这是现有动效的设计。逐帧绘制已限制在视口附近，文本排版复用缓存；100 / 1000 / 5000 行基准都只有 9 个候选行，歌词总行数不是这条持续卡顿路径的主要开销。

优化前，`LyricWordPainter` 对每个正在浮动的字素执行：

1. 一层带矩阵滤镜的离屏绘制，用双线性采样保留亚像素浮动。
2. 一层文字覆盖率遮罩。
3. 一层底色与高亮颜色合成。
4. 高亮尾部经过该词时，再增加一层渐隐遮罩。

周围行的透明度和距离模糊、视口上下边缘遮罩还会增加合成工作。每个字素又重复构建裁剪路径、合并矩形边界。原有 `apple_music_benchmark.dart` 只记录 Picture 的 CPU 耗时，无法覆盖这些栅格化开销。

这与 [Flutter 对 saveLayer 的说明](https://docs.flutter.dev/perf/best-practices#use-savelayer-thoughtfully)一致：离屏缓冲和渲染目标切换可能引发卡顿，移动 GPU 对此尤其敏感。这里定位到了代码中的合成热点；目前没有连接手机，尚未取得目标设备的 GPU trace 或实际帧率。

### 实现

- 把 Float 的离屏层直接作为文字覆盖率层，保留矩阵滤镜与双线性采样。
- 默认纯色高亮先合成底色与高亮色，再通过 `srcIn` 应用文字覆盖率。尾部渐隐通过 shader + `ColorFilter.mode(base, BlendMode.dstOver)` 完成，不再建立单独颜色层或尾部层。每个字素由 3–4 层降至 1 层。
- 自定义渐变仍保留颜色合成路径，浮动时也复用已有覆盖率层；不改变渐变坐标、透明度和尾部行为。
- 字素/单词裁剪路径、段落边界和词宽随排版结果延迟缓存，沿用原有排版失效与释放生命周期。

默认动效、距离模糊、文字大小、时间轴与公开 API 均不变，不需要迁移调用代码。

### 验证

`test/lyric_word_compositing_test.dart` 将新路径与独立的多层颜色合成参照做像素对比，覆盖透明/半透明/不透明底色、纯色/渐变高亮、部分/完整进度、换行、RTL、Word Pop、Float，以及 1x / 2.75x 像素密度。另有离屏层数回归，防止默认浮动重新引入每字多层嵌套。

新增 `test/benchmarks/apple_music_compositing_benchmark.dart` 使用 400 × 360 逻辑像素视口、3x 像素密度、100 行带翻译歌词、默认 Apple Music 动效，分别测量真实词时间戳与 LRC 模拟时间。每轮预热 10 帧、采样 60 帧，包含 pump、边缘遮罩、模糊、栅格化和 RGBA 回读；不是手机显示帧耗时。

```sh
flutter analyze --no-pub lib test
flutter test --no-pub
flutter test --no-pub --concurrency=1 \
  test/benchmarks/apple_music_benchmark.dart \
  test/benchmarks/apple_music_compositing_benchmark.dart --reporter expanded
```

对比时使用同一 Flutter SDK 串行运行优化前后版本；避免一边跑完整测试一边测性能。CPU Picture 记录与栅格化回读数据分别解读。

### 本机对比结果

2026-10-13，macOS arm64，Flutter 3.44.9 / Dart 3.12.2。优化前为 `05fa2ec` 的渲染实现，优化后为本次实现；两者使用同一份基准，每个版本串行运行 3 轮。下表采用各轮中位数的中位数，保留范围说明宿主机波动。

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 初始帧显式 Canvas 离屏层数 | 127 | 43（减少 66.1%） |
| 真实时间戳：pump + 栅格化 + 回读中位数 | 29.34 ms | 22.43 ms（减少 23.6%） |
| LRC 模拟时间：同上 | 26.95 ms | 22.09 ms（减少 18.0%） |
| 1000 行 CPU Picture 记录 | 67.6 µs/帧 | 51.4 µs/帧 |
| 5000 行 CPU Picture 记录 | 74.4 µs/帧 | 66.5 µs/帧 |

真实时间戳的三轮中位数分别为 29.03 / 30.46 / 29.34 ms 与 22.43 / 23.55 / 22.37 ms；模拟时间分别为 26.60 / 28.06 / 26.95 ms 与 21.83 / 23.56 / 22.09 ms。层数统计只包含 painter 显式调用的 `saveLayer`，不包含 Flutter 的边缘 ShaderMask 层或后端内部 pass；完整回读耗时包含边缘遮罩。采样发生在同一句歌词内部，切句和拖动仍需真机复核。

宿主回读和 debug 测试有额外开销，尤其 p90 会受进程调度影响。这些数据用于同环境前后对比，不能当作移动端 FPS 或 GPU 耗时。手机是否消除掉帧仍以 profile trace 为准。

### 真机复核

在目标手机上以 profile 模式运行 example，选择 Apple Music 风格并观察 Flutter DevTools 的 UI / raster 帧耗时。分别检查正常播放、切句、拖动、长歌词和暂停浮动。60 Hz 的每线程帧预算约为 16.7 ms，120 Hz 约为 8.3 ms；桌面回读基准不能用于推断手机是否满足这些预算。

本次保留距离模糊与边缘遮罩。若目标设备的 trace 仍显示模糊为瓶颈，可以结合现有 `distanceBlur` / `blurWhenBrowsing` 参数进一步评估；不应仅用 debug 模式的帧率判断最终效果。
